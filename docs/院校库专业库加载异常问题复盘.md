# 院校库 / 专业库加载异常问题复盘

## 基本信息

- 记录日期：2026-04-09
- 项目：VolunteerHelper 高考志愿填报助手
- 涉及模块：前端 Web、Nginx 反向代理、后端 API、PM2 部署
- 线上地址：
  - 公网主入口：`http://132.232.245.53`
  - 前端直连入口：`http://132.232.245.53:3004`
  - 后端服务：`http://127.0.0.1:3003`

## 问题现象

本次问题分为两个阶段：

### 第一阶段

- 移动端可以正常查看院校库、专业库。
- 电脑端打开院校库、专业库时，页面显示“暂无匹配的院校”或“暂无匹配的专业”。
- 实际上不是没有数据，而是接口请求失败后被页面错误地当成了“空数据”。

### 第二阶段

- 将前端 API 地址修正后，电脑端通过主入口可以正常加载院校库、专业库。
- 但部分访问方式又出现了移动端或手机访问时报 `404` 的情况。
- 进一步排查后确认，这并不是真正的“移动端和电脑端逻辑不同”，而是访问入口不同导致的行为不一致。

## 根因分析

## 1. 第一阶段的真实根因

前端生产环境原来使用的是绝对地址：

```env
NEXT_PUBLIC_API_URL=http://132.232.245.53:3003/api/v1
```

用户访问页面时使用的是：

```text
http://132.232.245.53
```

此时浏览器会从页面所在域名发起跨域请求到：

```text
http://132.232.245.53:3003/api/v1
```

但后端 CORS 只允许了部分来源，导致浏览器拦截请求。前端页面没有把“请求失败”明确展示出来，而是把失败结果渲染成了“暂无匹配的院校/专业”，因此造成误判。

也就是说：

- 不是数据库没有数据
- 不是筛选条件有问题
- 是浏览器请求被 CORS 阻止
- 且前端错误处理方式掩盖了真实异常

## 2. 第二阶段为什么会“顾此失彼”

为了解决第一阶段问题，前端被改为同源访问：

```env
NEXT_PUBLIC_API_URL=/api/v1
```

这个改动本身是正确的，因为它让 API 请求交给当前入口统一处理，避免跨域。

但是线上当前存在两个公网入口：

### 入口 A：主入口

```text
http://132.232.245.53
```

这个入口经过 Nginx，Nginx 会把：

```text
/api/*
```

反向代理到后端 `3003`，因此：

```text
http://132.232.245.53/api/v1/universities
```

可以正常返回 `200`。

### 入口 B：直连前端

```text
http://132.232.245.53:3004
```

这个入口直接访问 Next.js 服务本身，不经过 Nginx。  
而 Next.js 默认并不知道 `/api/v1/*` 需要转发给后端，因此：

```text
http://132.232.245.53:3004/api/v1/universities
```

会直接返回 `404`。

因此，问题的本质不是“移动端能访问、电脑端不能访问”，而是：

- 有人通过 `80` 端口访问，接口正常
- 有人通过 `3004` 端口访问，接口 `404`

如果手机端打开的是 `:3004` 这个地址，就会表现为“移动端 404”。

## 是否属于架构问题

是，属于部署入口设计不统一带来的架构问题，但不是前端页面架构本身崩溃。

当前线上实际是“双入口架构”：

- `80/443` 由 Nginx 对外提供服务
- `3004` 也被直接暴露给公网

这两个入口对 `/api` 的处理逻辑不一致，导致同一份前端代码在不同访问入口下行为不同。

这类架构会产生以下问题：

- 同一个页面在不同访问地址下表现不一致
- 前端使用相对路径时，依赖入口是否具备反向代理能力
- 排障时容易误以为是“设备适配问题”或“浏览器兼容问题”
- 后续新增接口或静态资源规则时容易再次出现类似问题

## 已实施的修复方案

## 1. 前端 API 改为同源访问

文件：

- `apps/web/src/services/api.ts`

处理方式：

- 将默认 API 地址改为 `/api/v1`
- 避免前端直接跨域请求 `3003`
- 让反向代理或统一入口处理后端转发

## 2. 页面错误状态显式展示

文件：

- `apps/web/src/app/(main)/universities/page.tsx`
- `apps/web/src/app/(main)/majors/page.tsx`

处理方式：

- 请求失败时不再伪装成“暂无匹配数据”
- 直接显示错误提示，方便用户和开发人员判断是真空数据还是请求失败

## 3. 为 `3004` 直连入口增加兼容 rewrite

文件：

- `apps/web/next.config.js`

处理方式：

- 新增 Next.js rewrite
- 将 `/api/:path*` 转发到内部后端地址 `http://127.0.0.1:3003/api/:path*`

这样即使用户直接访问：

```text
http://132.232.245.53:3004
```

前端发起的：

```text
/api/v1/*
```

也能正确转发到后端，而不是返回 `404`。

## 4. 处理前端生产构建中的字体依赖问题

文件：

- `apps/web/src/app/layout.tsx`
- `apps/web/src/app/globals.css`

处理方式：

- 去掉 `next/font/google`
- 改为本地 CSS 字体栈

原因：

- 线上构建时 Google Fonts 拉取超时，阻塞了修复版本发布
- 该处理是为了保证生产构建稳定完成

## 5. 修复自动部署脚本的同步缺口

文件：

- `deploy_auto.py`

处理方式：

- 部署时除了上传 `.next` 产物，还同步上传：
  - `apps/web/next.config.js`
  - `apps/web/.env.production.local`
  - `apps/web/package.json`

原因：

- 如果只上传 `.next`，而线上运行配置文件仍是旧版本，就会出现“代码已修复、运行配置未生效”的情况
- 本次问题里，`next.config.js` 就属于关键运行配置文件

## 验证结果

修复前验证结果：

```text
http://132.232.245.53/api/v1/universities?page=1&pageSize=1       => 200
http://132.232.245.53:3004/api/v1/universities?page=1&pageSize=1  => 404
http://132.232.245.53/api/v1/majors?page=1&pageSize=1             => 200
http://132.232.245.53:3004/api/v1/majors?page=1&pageSize=1        => 404
```

修复并重新部署后验证结果：

```text
http://132.232.245.53/api/v1/universities?page=1&pageSize=1       => 200
http://132.232.245.53:3004/api/v1/universities?page=1&pageSize=1  => 200
http://132.232.245.53/api/v1/majors?page=1&pageSize=1             => 200
http://132.232.245.53:3004/api/v1/majors?page=1&pageSize=1        => 200
```

说明：

- 主入口已正常
- 直连 `3004` 入口也已具备兼容能力
- 院校库和专业库都已恢复正常访问

## 长期建议

本次问题虽然已经修复，但长期来看仍建议进一步收敛部署架构。

### 推荐方案

- 只对外暴露 `80/443`
- `3003` 和 `3004` 仅允许服务器内网访问
- Nginx 作为唯一公网入口
- 前端始终使用 `/api/v1` 这样的同源路径

### 这样做的好处

- 用户无论使用电脑还是手机，都只会访问同一个标准入口
- API 路由行为统一，不会再因入口不同而产生差异
- CORS、Cookie、鉴权、静态资源路径都更容易统一管理
- 部署和排障成本更低

## 结论

本次问题并不是“移动端页面”和“电脑端页面”互相冲突，也不是数据库没有数据。  
根因是线上存在两个公网入口，而这两个入口对 `/api` 的处理逻辑不同，导致前端在切换为同源 API 后，主入口正常、直连端口却返回 `404`。

当前已经完成以下闭环：

- 修复前端 API 调用方式
- 修复前端错误展示方式
- 为 `3004` 直连入口增加 rewrite 兼容
- 解决构建阻塞问题
- 修复自动部署脚本的配置同步缺口
- 完成线上部署与接口验证

目前该问题已恢复正常。
