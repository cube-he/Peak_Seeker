## 0. 怎么用这份文档

这是一份**契约文档**，不是视觉规范。它回答三个问题：

1. **页面要显示什么？** —— 后端给的每一个字段、每一种取值（§3 §4 §8）
2. **页面有多少种样子？** —— 全部状态/空态/错误态/边界态（§9）
3. **点了会发生什么？** —— 每个交互的结果（§10）

**设计自由度**：配色、字体、间距、圆角、阴影、图标风格、布局排版、动效 —— 全部由你定。
**不可破坏的契约**：数据字段不能漏、不能发明后端没有的字段；状态机（4 种资格判定 × 三段分区 × 折叠两层）不能改；交互流程（勾选→提交、锁定→解锁、资料缺失拦截）不能改。详见 §11。

**交付要求**：设计稿里每个动态元素请标注它绑定的字段名（例如「这个绿标签 = `verdict`」），方便开发复现时精确对应。详见 §12。

## 1. 这个页面是干什么的（一句话业务背景）

四川新高考志愿填报系统里，**老师**给**某个学生**筛选「能报哪些录取批次」。系统按学生资料（选科 / 分数 / 户籍 / 民族 / 性别 / 出生日期 / 体检数据）自动判定每个批次及其下子类别的**报考资格**，老师在此页**勾选**最终要为该学生制作方案的批次并**提交锁定**。提交后，这些批次会成为「方案生成页」的可用范围。

关键词：**这是判定「资格」的页面，不是判定「能不能考上」的页面**。分数信息只作展示参考（够不够线），录取概率不在这里算。

---

## 2. 用户与场景

- **角色**：老师（也可主管/管理员查看）。一个老师同时带多个学生，需要**秒级判断**当前学生的批次格局。
- **设备**：主要桌面浏览器（老师在电脑上办公）。建议做窄屏自适应但不必移动优先。
- **高频动作**：扫一眼学生概览 → 看「符合」段有哪些 → 勾几个 → 提交。偶尔展开看某批次的子类别细节和政策文件。

---

## 3. 数据从哪来（API 端点）

页面加载时前端并发取两个接口，合并成一个视图模型：

| 时机 | 方法 | 端点 | 返回 |
|---|---|---|---|
| 进页面 | GET | `/students/:id/eligible-batches` | `{ batches, intakeGap }` |
| 进页面 | GET | `/students/:id` | 学生详情（取其中 8 个字段拼 `student` 概览 + `batchesConfirmedAt` + `preferredBatches`） |
| 点「确认并提交」 | POST | `/students/:id/confirm-batches` | body `{ preferredBatches: string[], reviewComment?: string }` |
| 点「重新打开」 | POST | `/students/:id/unlock-batches` | body `{}`，成功后重新拉取整页 |

合并后的视图模型 `BatchRecommendationsResponse`（前端实际持有的数据，设计就按这个结构理解）：

```ts
{
  batches: BatchRecommendation[];        // 该学生所有候选批次（已含资格判定）
  batchesConfirmedAt: string | null;     // 非空 = 已锁定（ISO 时间串）
  preferredBatches: string[] | null;     // 上次确认时选定的批次名数组；null = 从未确认
  intakeGap: { ok: boolean; missing: { field: string; label: string }[] };
  student: StudentSummary;               // 顶部概览条数据
}
```

## 4. 完整数据契约（每个字段都要能映射到一个 UI 元素）

### 4.1 `student`（顶部概览条）

```ts
interface StudentSummary {
  id: number;
  realName: string | null;          // 姓名；null 时显示「学生 {id}」
  examType: string | null;          // 选科类别枚举，见 §8.1
  examYear: number | null;          // 高考年份，如 2026
  totalScore: number | null;        // 高考总分
  provincialRank: number | null;    // 全省位次（展示用千分位）
  firstChoice: string | null;       // 首选科目（物理/历史）
  reChoices: string[] | null;       // 再选科目数组（如 ["化学","生物"]）
  intakeReviewComment: string | null;// 上次老师备注（锁定条里回显）
}
```

概览条文案拼法：
- 姓名：`realName ?? "学生 {id}"`，加粗最大字号
- 选科：若 `firstChoice` 且 `reChoices` 非空 → `「{examType中文} · {firstChoice} · {reChoices.join('/')}」`，否则只显示 `{examType中文}`
- 总分 / 位次 / 高考年份：缺值显示 `--`；位次用千分位（`12,345`）

### 4.2 `batches[]`（核心列表）

```ts
interface BatchRecommendation {
  batchConfigId: number;     // React key
  batchName: string;         // 批次名，如「本科提前批A段」「高职（专科）批」
  volunteerMode: string;     // 志愿模式枚举，见 §8.4
  admissionOrder: number;    // 录取顺序（后端已按此排序，前端不再排）
  verdict: Verdict;          // 该批次总判定，见 §8.2
  reasons: { type: string; message: string }[];  // 判定理由（兜底文案用）
  subsetResults?: SubsetResult[];  // 子类别明细（展开后显示）；可能为空
  scoreInfo?: ScoreInfo;           // 分数信息（仅展示参考）；可能为空
}
```

### 4.3 `SubsetResult`（批次下的子类别，如「军队院校」「国家专项」）

```ts
interface SubsetResult {
  code: string;
  name: string;          // 子类别名，如「军队院校」
  description: string;   // 一段说明文字
  verdict: Verdict;      // 子类别判定，见 §8.2（与批次同枚举）
  rulesEval: {           // 逐条规则判定（展开子类别后逐行显示）
    ruleCode: string;
    requirement: string; // 要求（中文短语），如「裸眼视力下限」「身高下限」
    actual: string;      // 实际/结论文案，如「需两眼裸眼 ≥4.8，学生最差眼 4.2 不达标」
    pass: 'PASS' | 'FAIL' | 'UNCERTAIN' | 'SOFT_HINT';  // 见 §8.3
  }[];
  references: ReferenceItem[];  // 该子类别的相关政策文件
}
```

### 4.4 `ReferenceItem`（政策文件/官网链接）

```ts
interface ReferenceItem {
  title: string;            // 文件标题
  filename: string | null;
  type: 'pdf' | 'xlsx' | 'doc' | 'announcement';  // 决定图标，见 §8.5
  downloadUrl: string | null;
  available: boolean;       // false = 文件还没上传，显示「文件待补」
  sourceNote?: string;      // 待补时的补充说明
  external?: boolean;       // true = 外站官网链接，只显示「查看官网」
}
```

三种渲染态（务必都设计）见 §7.9。

### 4.5 `ScoreInfo`（分数参考，仅展示不影响资格）

```ts
interface ScoreInfo {
  studentScore: number | null;
  lineScore: number | null;
  lineType: 'BATCH_LINE' | 'SPECIAL_LINE' | 'ZHUANKE_LINE';  // 线种类，见 §8.6
  lineMissing: boolean;       // 当年该线数据缺失
  gap: number | null;         // studentScore - lineScore
  passesLine: boolean | null; // 是否过线
  leniency?: number;          // 容错分（如提前批 B 段 20 分）
  withinLeniency: boolean | null; // 不过线但在容错内
}
```

### 4.6 `intakeGap`（学生关键资料是否齐全）

```ts
{ ok: boolean; missing: { field: string; label: string }[] }
```

后端要求 6 项必填才能准确判定资格：**选科 / 户籍县 / 城乡户籍 / 出生日期 / 民族 / 性别**。任一缺失 → `ok=false`，`missing` 列出缺的项（`label` 是中文名，直接展示）。`ok=false` 时：① 顶部红色警告框；② **底部提交按钮 disabled**，文案变「资料未完成 - 无法确认」。

## 7. 区块逐个规格

### 7.1 学生概览条
- 一行（窄屏可折行）展示：姓名（最大/加粗）、选科、总分、位次、高考年份。
- 数据见 §4.1。这是老师秒判学生的锚点，信息密度要高、可一眼扫完。

### 7.2 锁定提示条（条件显示）
- **仅当** `batchesConfirmedAt` 非空（已锁定）时出现。
- 内容：`已锁定: {本地时间}` + 若有 `intakeReviewComment` 追加 `· 上次备注: {内容}` + 「重新打开」按钮。
- 语义：警示色（当前实现黄底）。
- 锁定态下：所有勾选/全选/清空禁用，底部提交栏**不出现**（见 §9 锁定态）。

### 7.3 标题行 + 说明条
- 标题「批次推荐」+ 右侧「← 返回学生详情」链接（跳 `/teacher/students/:id`）。
- 说明条（中性灰）：固定文案「ℹ 勾选某批次 = 让方案生成可用该批次下**所有「资格通过」**的子类别（例如本科批A段会包含普通类等）。点批次卡片可展开看子类别 + 相关文件。」

### 7.4 资料缺失警告框（条件显示）
- **仅当** `intakeGap.ok === false` 时出现，危险色（当前红）。
- 内容：标题「⚠ 学生关键资料未完成 — 当前判定可能不准」+ 一行「缺失字段: {missing 的 label 用 ` / ` 连接}」+ 链接「→ 跳学生详情页催补资料」。

### 7.5 工具条
- **搜索框**：占位符「搜批次名 (例如: 高职 / 本科批A)」，实时过滤（按 `batchName.includes`，仅匹配批次名，不搜子类别）。
- **「全选符合资格 (N)」按钮**：N = `verdict ∈ {ELIGIBLE, CONDITIONAL}` 的批次数（**注意：不含 DATA_PENDING**）。点击把这些批次全部勾上。锁定/提交中禁用。
- **「清空已选」按钮**：清空所有勾选。已选为 0 或锁定/提交中时禁用。

### 7.6 三段 Section + 段头
三段固定顺序，每段一个段头（标题 + 数量徽标 + 右侧灰色 hint）：

| 段 | 标题 | 语义色 | hint | 归入条件 |
|---|---|---|---|---|
| 1 | 已选批次 | 强调（蓝） | 勾选/取消会同步到方案生成页可用范围 | `selected.has(batchName)`（不论 verdict） |
| 2 | 符合填报条件 | 成功（绿） | 可勾选进推荐 | 未选 且 `verdict ∈ {ELIGIBLE, CONDITIONAL, DATA_PENDING}` |
| 3 | 不符合条件 | 危险（红） | 硬性资格未满足 — 通常不建议勾选 | 未选 且 `verdict === INELIGIBLE` |

- **分段是动态的**：勾选一个「符合」段的批次，它立刻移到「已选」段；取消则移回原段。设计需考虑这种重排（卡片在三段间移动）。
- **空段**：该段无批次时显示一句灰字占位（已选段：「还没选, 在下方"符合填报条件"段勾选」；其余段：「无」）。搜索过滤后也可能某段为空。
- ⚠ 注意 §7.5 的「全选」与 §7.6 第 2 段的归属**口径不同**：第 2 段包含 DATA_PENDING，但「全选符合资格」不选 DATA_PENDING。设计文案上不必解释，但开发复现时要严格区分。

### 7.7 批次卡片 BatchCard（**默认折叠**，可展开）

**折叠态（header，永远可见）**——这是老师扫读的主视图，信息要全在这一行块里：
- 左：勾选框 `checkbox`（绑定该批次是否在 `selected`）
- 中：
  - 批次名（加粗）= `batchName`
  - 副行「志愿模式: {中文}」= `volunteerMode`（见 §8.4）
  - **一句话摘要**（关键！collapsed 也能判断）= 按 `verdict` 生成，见下表
- 右：`verdict` 彩色标签（见 §8.2）+「展开 ▼ / 收起 ▲」

一句话摘要（`summary`）生成规则：

| verdict | 摘要内容 |
|---|---|
| INELIGIBLE | 第一条 `pass=FAIL` 的子规则「{requirement} → {actual}」；没有则取 HARD_FAIL 理由；再没有则「硬性资格未满足 (展开看详情)」 |
| CONDITIONAL | 第一条 `pass ∈ {UNCERTAIN, SOFT_HINT}` 的「待核实: {requirement}」；没有则「部分条件需老师核实」 |
| DATA_PENDING | 「子类别详情待补充 — 展开看」 |
| ELIGIBLE | 分差「{±}{gap} 分 (你 {studentScore} / 线 {lineScore})」（有分数线时）；否则「资格通过」 |

**展开态（body）**：
- `ScoreInfo` 行（见 §7.8.A，若有 `scoreInfo`）
- 「子类别 / 资格判定:」标题 + 子类别列表（每个一个 §7.8 SubsetItem）
- 若 `subsetResults` 为空：显示「无子类别信息」

### 7.8 展开态的两个子组件

**A. 分数信息行 ScoreInfoRow**（绑定 `scoreInfo`）——分档配色：
- `lineMissing=true` → 中性灰「当年 {线名} 数据缺失」
- `studentScore` 或 `lineScore` 缺 → 中性灰「{线名}: {值/?}，学生总分: {值/未填}」
- 正常 → 「你 {studentScore} / {线名} {lineScore} ({±}{gap} 分)」，配色按分差分档：
  - `gap ≥ 30` 成功绿 / `gap ≥ 0` 信息蓝 / `withinLeniency` 警示黄 / 否则危险红
  - 若在容错内（`leniency` 且未过线且 `withinLeniency`）追加「— 在 {leniency} 分容错内」
- 线名映射见 §8.6。

**B. 子类别项 SubsetItem**（绑定一个 `SubsetResult`，**自身也可折叠/展开**）：
- 折叠态：`name` +「[{verdict 中文}]」+ 一句话原因（第一条 FAIL 的 requirement，否则第一条 SOFT_HINT 的 requirement，否则 `description`）+「展开 ▼/收起 ▲」
- 展开态：`description` 全文 + `rulesEval` 逐条列表（每条：`pass` 图标 + 「{requirement}: {actual}」，图标见 §8.3）+ 相关文件列表（§7.9）

> 这是一个**两层折叠**结构：批次卡片展开 → 看到若干子类别；子类别再展开 → 看到逐条规则 + 文件。设计需明确两层的视觉缩进/层级关系。

### 7.9 相关文件列表 ReferencesList（每个 `ReferenceItem` 三态，务必都设计）
每行：类型图标（§8.5）+ 标题，后跟操作链接——

| 条件 | 渲染 |
|---|---|
| `available && external` | 一个链接「查看官网」（新窗口打开 `downloadUrl`） |
| `available && !external` | 「预览」+「下载」两个链接。预览：pdf 用原 URL，doc/xlsx 用同名 `.preview.pdf`（服务器已用 LibreOffice 预转）；下载：`{downloadUrl}?download=1` |
| `!available` | 灰色斜体「文件待补」，若有 `sourceNote` 追加「— {sourceNote}」，无可点链接 |

### 7.10 底部提交栏（sticky 吸底，**仅未锁定时显示**）
自上而下：
1. **已选 chip 列表**：「已选 **{N}** 个批次:」+ 每个已选批次一个圆角 chip（批次名 + 可点的 `×` 取消）。N=0 时显示灰色斜体「(未选)」。
2. **覆盖警告**（仅 `batchesConfirmedAt` 非空时）：警示色小条「⚠ 上次已确认 {日期}，提交会**覆盖**上次选择 + 影响方案生成页可用批次」。
3. **备注 textarea**：占位符「老师备注 (可选, 例如: 学生想冲强基, 我担心保不住二本)」，2 行。
4. **「确认并提交」按钮**：主按钮。disabled 条件：`submitting || selected.size===0 || intakeGap.ok===false`。当 `intakeGap.ok===false` 时按钮文案变「资料未完成 - 无法确认」。

### 7.11 提交 / 解锁的后端语义（成功后发生什么 + 会怎样失败）★这俩不是纯前端动作

这两个写操作后端有重要副作用和校验，设计「成功反馈」「失败反馈」时必须知道：

**「确认并提交」（`confirm-batches`）成功 = 一个动作干三件事**：
1. 写入 `preferredBatches` → 成为「方案生成页」的可用批次范围
2. `batchesConfirmedAt` 置当前时间 → 页面进入**锁定态**
3. **`intakeStatus` 推进到 VERIFIED（学生资料视为「已核验」）** + 记录审核人/时间/备注

> ⚠ 第 3 点是隐藏语义：提交批次会**顺带把学生资料标记为已核验**。文案建议让老师明白「确认并提交」= 锁定批次 + 确认资料，不是单纯存一下勾选。成功后跳转 `/teacher/students/:id`。

**「确认并提交」会失败的 5 种情况**（后端抛错，消息显示在页面顶部错误区，红字 —— 设计要准备这个错误展示态）：

| 失败原因 | 后端返回文案 |
|---|---|
| 没勾任何批次 | 至少选定 1 个批次 |
| 勾了后端白名单外的批次名 | 未知批次: {名} |
| 学生还没提交资料（intakeStatus=DRAFT） | 学生尚未提交资料, 无法选定批次 |
| 关键资料缺失（后端二次校验，即使前端已 disable） | 学生关键资料未完成, 请催学生补完后再确认批次: {缺失项} |
| 操作者不是该生带班老师 | 无权确认不属于自己的学生的批次 |

> 前端虽对「空选 / 资料缺失」做了按钮 disable（§7.10），后端仍二次校验兜底。所以「提交失败」是一个真实会出现的态，别只设计成功路径。

**「重新打开」（`unlock-batches`）成功 = 三件事**：
1. `batchesConfirmedAt` 置空 → 解除锁定
2. **`intakeStatus` 打回 NEEDS_CHANGES（学生需重新修改资料）** + 记录解锁人/时间
3. 前端重新拉取整页，回到可编辑态

> 解锁是有后果的操作（把学生打回「需修改」），已有浏览器二次确认弹窗。若批次本就未锁定，后端不报错、静默返回（按钮只在锁定态出现，正常碰不到）；越权解锁 → 报错「无权解锁该学生的批次」。

## 9. 全部状态/边界态清单（★设计稿必须逐个覆盖，别只画理想态）

页面级：
1. **加载中**：`data` 未到 → 「加载中…」
2. **加载失败（API）**：`error` 非空 → 红字「加载失败: {错误}」（整页只有这一行）。越权访问/网络错误都走这里。
3. **正常态**：见下面各组合
4. **锁定态**（`batchesConfirmedAt` 非空）：显示锁定条；所有 checkbox / 全选 / 清空禁用；**底部提交栏不出现**；卡片只读浏览。
5. **资料缺失态**（`intakeGap.ok=false`）：顶部红警告框；提交按钮禁用且文案变化（可与正常态叠加——即资料缺失但未锁定）。
6. **提交失败态**：点提交后后端校验未过（§7.11 的 5 种原因），错误消息显示在页面顶部错误区（与第 2 条加载失败同位置，红字），按钮恢复可点。
7. **全页崩溃态**（Next 错误边界 `error.tsx`，与第 2 条不同）：组件渲染抛异常时整页接管，显示「页面加载出错」+ 错误消息 +（若有）错误 ID + 「刚部署可能是缓存，请 Ctrl+Shift+R 硬刷新」提示 + 「重试」「刷新页面」两个按钮。需提供这个独立全页错误态。

列表级：
8. **某段为空**：占位灰字（已选段 / 符合段 / 不符合段各有文案）。
9. **搜索无结果**：三段可能全空，各显占位。
10. **已选段含 INELIGIBLE**：老师可以硬勾一个「不符合」的批次，它会出现在已选段并带红标签——已选段卡片要能显示任意 verdict。

卡片级（每种 verdict 都要有折叠态 + 展开态两版）：

## 11. 设计自由 vs 不可破坏的契约

**你可以自由决定**：整体视觉风格、配色方案、字体、卡片样式、圆角阴影、留白、图标库、段落排版、徽标样式、动效与过渡、响应式断点、是否用抽屉/手风琴/标签页重组信息。

**必须保留（否则与后端脱节）**：
1. **不发明字段、不漏字段**：§4 列出的字段都要有去处；后端没有的数据（如录取概率、推荐分数排名）不要在此页编造。
2. **4 种 verdict 视觉可区分**（成功/警示/危险/中性），批次级和子类别级都用同一套。
3. **4 种 pass 状态可区分**（✓/✗/?/ℹ 或等效视觉）。
4. **三段分区 + 归属规则**（§7.6），且分区随勾选动态重排。
5. **两层折叠结构**（批次 → 子类别 → 规则/文件），且折叠态必须带「一句话摘要」让老师不展开也能判断。
6. **勾选→底部提交**全链路，含 disabled 条件（空选 / 资料缺失）与文案变化。
7. **锁定/解锁**机制与只读态。
8. **资料缺失拦截**（顶部警告 + 提交禁用）。
9. **文件三态**（预览下载 / 查看官网 / 待补）。
10. **分数仅作参考**的定位——不要把 ScoreInfo 设计得像「录取概率/推荐度」，避免误导老师以为这是能否考上的判断。

## 附录 C：已知后端缺陷 / 增强点（设计前须知，**非设计任务**）

> 这些是核查中发现的后端问题，列出让设计与开发都心里有数。应在重做前端时一并修复，**不要被当成「特性」设计进去**。

### C1【已修】提交批次的白名单与实际批次脱节
- 旧实现：`confirmBatches` 用硬编码白名单（仅 6 项），与 batchConfig 实际定义的 22 个批次交集只有 5 个。勾「强基计划」「各类专项」等 17 个会被后端拒为「未知批次」。

- 设计影响：**全部 22 个批次都可提交**，设计按全量来。

### C2【增强点】分数线「往年预估」未在前端体现
- 后端在当年（2026）分数线缺失时回退用上一年（2025）线预估，并在 `scoreInfo` 打 `lineYearUsed` 标记。
- 但前端 `ScoreInfo` 类型没有该字段、分数行也没展示——老师无法区分「今年实际线 vs 往年预估线」。
- **建议**：后端把 `lineYearUsed` 透出，前端在分数行加一句「（按 2025 年线预估）」。设计可预留这个小标注位。

## 附录 D：后端行为对设计的具体影响（★ claude design 必读）

> 这一节回答一个问题：**后端这样工作，前端设计必须呈现什么 / 必须能承受什么**。每条都给「后端事实 → 设计含义」。

### D1 学生 `intakeStatus` 四态决定本页的渲染分支

后端有 4 种状态，提交/解锁的可行性、页面是否锁定，全由它驱动：

| intakeStatus | 怎么进来 | 本页表现 |
|---|---|---|
| **DRAFT** | 学生还在自己填资料，没点过「提交资料」 | 通常进不来本页（详情页拦住）；硬进来后端会拒绝 confirm，报「学生尚未提交资料」 |
| **SUBMITTED** | 学生填完点「提交资料」，老师还没确认过 | 正常态，可勾选可提交 |
| **NEEDS_CHANGES** | ① 老师在本页点过「重新打开」；② 老师在详情页点过「要求修改」 | 跟 SUBMITTED 一样的正常态，**学生不需要再提交一次**，老师可直接重新 confirm |
| **VERIFIED** | 老师在本页或详情页确认过 | 进入**锁定态**，本页只读；要改必须先「重新打开」 |

设计含义：
- 锁定/未锁定的视觉切换只看 `batchesConfirmedAt` 是否为空（不要再引入 `intakeStatus` 的另一套视觉）。
- 「重新打开」按钮文案别写「让学生重新填」——它的真实语义是「老师要改批次」，学生资料不动也行。

### D2 位次 + 分数线 **双重往年回退**，设计要留两处「往年估值」标注

后端有两处当年数据缺失时会回退用上一年估算，且独立触发：

| 字段 | 缺失时回退到 | 后端标记 | 出现位置 |
|---|---|---|---|
| 学生概览条的 `provincialRank` | 用 2025 一分一段表估算 | `rankCheck.isEstimated=true`, `sourceYear=2025` | §7.1 概览条「位次」 |
| 卡片分数行的批次/特殊/专科线 | 用 2025 同种线 | `scoreInfo.lineYearUsed=2025` | §7.8.A 分数信息行 |

设计含义：这两处都要留一个小灰色尾注位（如「（按 2025 估）」），让老师明白数据来源。两者独立——可能其中一个回退、另一个真实。

> 这一条把附录 C 的 C2 升级了：不只是分数线要标注，位次也要。

### D3 选「文综/理综」的学生**算不出位次**，概览条会显示 "--"

后端 examType 是 `COMPREHENSIVE_SCIENCE` / `COMPREHENSIVE_LIBERAL`（旧高考残留值）时，位次接口返回 null。概览条「位次: --」是**正常态**，不是 error。

设计含义：不要给这个 "--" 加红色感叹号 / 警告色。新高考 2025+ 四川已经不会出现这两个值（前端选项也删了），仅旧数据兼容，可按"罕见但合法"对待。

### D4「未填」在子类规则里有**两种结局**，视觉必须分得开

子类展开后的规则列表（rulesEval）每条 `pass` 4 种状态（§8.3），其中 `FAIL` 和 `SOFT_HINT` 都可能由"学生没填"触发——但语义完全不同，老师的下一步动作也不同：

| 触发场景 | pass 值 | 老师该做什么 | 设计应表达 |
|---|---|---|---|
| 学生**客观**字段未填（户籍县 / 出生日期 / 民族 / 性别 / 身高 / 体重 / 裸眼视力 / 色觉） | **FAIL** ✗ | 催学生补资料 | 「资格不符」红/红框 |
| **主观**面谈才能定的项未填（政治考核 / 体检结论 / 服务承诺 / 校长推荐） | **SOFT_HINT** ℹ | 自己面谈核实 | 「需核实」黄/中性提示 |

两个反差强烈的例子：
- **色觉**未填 → FAIL（严格态度，把它当不达标，老师无法替学生宣布"色觉正常"）
- **政治考核**未填 → SOFT_HINT（系统不替老师判，必须老师面谈）

设计含义：✗ 和 ℹ 两个图标 + 配色**不能用同一个灰**，否则老师区分不出"我能催学生补"vs"我得自己面谈"。

### D5 子类规则的「要求」短语**可能直接显示英文规则码**（兼容边界）

后端维护规则码 → 中文短语字典（14 项，见附录 B）。如果后端新增规则码但字典没更新，或后端规则配错，`rulesEval[].requirement` 会**直接显示英文规则码**（如 `HEIGHT_MIN_BY_GENDER`）而非中文。

设计含义：规则列表的「要求」列必须兼容**纯英文短语**，不能假设只有汉字宽度就排版崩溃。

### D6 `verdict=DATA_PENDING` 的真正语义：**规则没配齐**，不是"学生不符合"

很容易把这态设计成红/黄"待补充"感叹号——但后端实际触发条件是：子类的 `dataPending=true` 标记位被设上（系统的规则字典本身还没配完整），跟学生填没填毫无关系。

设计含义：「详情待补充」配色/文案要**中性偏"系统状态"**（如灰底 + 蓝字 + 信息图标）——**不要**用红/黄这种暗示「学生有问题」的色。可考虑文案「规则待完善 — 展开看」。

### D7 长文本/自由文本字段，规则列表必须自动换行

子类规则展开后的 `actual` 列会出现这些长字符串/自由文本——结论列宽度必须容纳 + 自动换行，**不能** `ellipsis` 截断：

| 来源 | 例 |
|---|---|
| BMI 男女分开 | 「需 BMI 男 17.5-30 / 女 17-24, 学生未填性别 → 请先催学生补完资料」 |
| 视力详细 | 「需两眼裸眼 ≥4.5（矫正不算），学生最差眼 4.2 不达标（L:4.8 R:4.2）」 |
| 政治考核含 `politicalStatus` | 「需通过政治考核 (学生当前: 中共党员), 请老师面谈核实」（politicalStatus 是老师手填的自由文本，长度任意） |

### D8「确认并提交」**= 锁定批次 + 同时把学生资料推到「已核验」**

§7.11 已写过这条"一个动作干三件事"，这里强调它对**文案设计**的影响：
- 按钮文案不要只写「锁定批次」「保存选择」——它会**顺带把学生 intakeStatus 推进到 VERIFIED**（已核验）。
- 备注 textarea 提交后会写入 `intakeReviewComment`，这条备注**跨页面共享**——学生详情页的「上次审核备注」、本页锁定条的「上次备注: …」回显，读的都是它。设计上下文要明白这条备注的影响范围不局限于本页。

### D9 备注 textarea：**每次提交都是新增**，不是编辑上一条

老师本页 textarea 的占位文案「老师备注 (可选)」，提交时直接覆盖写到 `intakeReviewComment`（覆盖上一条）。textarea 的初值是空，不预填上次备注。

设计含义：textarea 上方建议补一句小灰字提示「（提交将覆盖上次备注）」，避免老师误以为留空就是保留上一条。锁定条里的「上次备注: …」单独回显，与 textarea 不耦合。
