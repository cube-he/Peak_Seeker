## 二、优先级分层

### P0 — 异常批次（需先调查再复核）

这些批次的数据模式异常，不能直接用标准流程处理，需要先人工判断。

| 批次 | 绿色 | 红色 | 总行数 | 异常原因 |
|------|------|------|--------|---------|
| 4429 | 2,711 | 0 | 2,711 | **100% 绿色** — 整个文件都是补录行，等同于全新 OCR，需确认是否第一轮 OCR 完全失败 |
| 4433 | 282 | 0 | 1,461 | 19% 绿色，涉及 102 个页面，补录量极大 |

**处理方式**：先读取原始 OCR xlsx 和前几张图片，判断第一轮 OCR 质量。如果 OCR 质量极差（>50% 错误），应考虑重跑 OCR 而非逐行复核。

### P1 — 有红色行的批次（需红绿配对分析）

红色行表示"OCR 有但图片无"，但根据人工发现，很多红色行实际是有效数据，仅因 O/0 字母混淆等单字段差异被误判。

| 批次 | 绿色 | 红色 | 总行数 | 需读图页数 |
|------|------|------|--------|----------|
| 3851 | 62 | 47 | 1,090 | 19 |
| 3336（88img） | 151 | 22 | 1,740 | 36 |
| 3321 | 42 | 3 | 219 | 8 |

**核心任务**：
1. 找出同一页面中红色行和绿色行的**配对关系**（同院校代码、大部分字段相同、仅 1 个字段不同）
2. 如果是配对的：保留正确版本，删除错误版本（通常红色是错的，绿色是对的）
3. 如果红色行没有配对绿色行：需要读图确认该数据是否真的不在图片中

## 三、页码-图片映射规则

**这是第二轮复核最关键的前置步骤。** 第一轮校验中页码可能有偏移。

### 已知的两种命名模式

| 模式 | 批次范围 | 图片起始 | 说明 |
|------|---------|---------|------|
| 从 `_001` 开始 | 2023 年批次（3264–3340） | `{batch}_001.png/jpg` | 图片序号 ≈ 文档印刷页码（部分有偏移） |
| 从 `_000` 开始 | 2024后期 + 2025 批次 | `{batch}_000.png/jpg` | `_000` 通常对应封面或第一页 |

### 已知的偏移案例

| 批次 | 图片文件 | 实际印刷页码 | 偏移量 | 说明 |
|------|---------|------------|--------|------|
| 3335（文科） | 3335_004.png | — 4 — | 0 | 图片序号 = 页码 |
| 3336（理科，88img） | 3336_001.png | — 74 — | +73 | 接在3335文科后面，页码连续 |

### 文理配对批次（页码连续，需要特别注意偏移）

| 文科批次 | 理科批次 | 关系 |
|---------|---------|------|
| 3335 | 3336 | 2023专科批第一次 |
| 3338 | 3339 | 2023专科批第一次（少数民族） |
| 3850 | 3851 | 2024专科批第一次 |
| 4428 | 4429 | 2025专科批第一次 |
| 4433 | 4434 | 2025专科批第二次 |

**每个 Agent 的第一步操作**：读取该批次第一张和最后一张图片，记录底部印刷页码，计算偏移量 `offset = 印刷页码 - 图片序号`。

## 四、复核规则

### 4.1 绿色行（缺漏补录）验证

1. 根据绿色行的页码，计算对应图片文件名：`{batch}_{页码-offset:03d}.png/jpg`
2. 用 Read 工具读取该图片
3. 在图片中查找该院校代码 + 专业代码
4. 核对：专业名称、计划数、收费、备注 是否一致
5. **跨页继承**：如果绿色行标注"跨页续行丢失"，院校信息在上一页末尾，本页只有专业行。需要同时读上一页确认院校信息

### 4.2 红色行（多余行）验证

1. 先检查同一页是否有**配对的绿色行**：
   - 同一院校代码
   - 大部分字段值相同
   - 仅 1-2 个字段不同（典型：专业代码 O→0、院校名称缺少"(民办院校)"）
2. **有配对**：这是 OCR 错误修正。红色行是错误版本，绿色行是正确版本。验证绿色行数据正确即可，红色行应删除
3. **无配对**：需要读图确认。如果图片中确实有该数据，则红色行是误判，应改为正常行

### 4.3 已知的典型 OCR 错误模式（红绿配对的特征）

| 错误类型 | 红色行特征 | 绿色行特征 | 判别方法 |
|---------|----------|----------|---------|
| O/0 混淆 | 专业代码含字母 O（如 OE, OX, OH） | 专业代码含数字 0（如 0E, 0X, 0H） | 其余字段完全相同 |
| 院校名称截断 | 缺少"(民办院校)"后缀 | 包含"(民办院校)" | 院校代码相同 |
| 院校代码错误 | 代码与其他行不同 | 代码正确 | 查看图片原文 |

## 五、Agent 并行策略

### 5.1 约束条件

- 所有 Agent 必须使用 **Opus 4.6 (1M 上下文)** 模型，不可使用其他模型
- **始终保持 5 个 Agent 并行运行**，完成 1 个立刻补 1 个（滚动执行）
- 每个 Agent 处理 1 个批次（大批次）或多个小批次（P3 合并）
- Agent 只读取有绿色/红色行的页面对应的图片，不全量读取
- 每个 Agent 输出 JSON 格式的复核报告
- 追求**绝对精准**：每行数据都要与原始图片逐字比对

## 六、Agent 执行规范

### 6.1 每个 Agent 的标准流程

```
1. 确定页码-图片映射
   a. 读取第一张图片，记录底部印刷页码
   b. 计算 offset = 印刷页码 - 图片序号
   c. 验证：读取另一张图片确认 offset 一致

2. 读取已校验 xlsx，提取所有绿色行和红色行
   a. 按页码分组
   b. 对红色行，查找同页同院校的绿色行配对

3. 逐页复核
   a. 计算图片文件名：{batch}_{页码-offset:03d}.png/jpg
   b. 用 Read 工具读取图片
   c. 对照绿色行：确认图片中是否存在该数据
   d. 对照红色行：确认图片中是否存在该数据
   e. 记录结果

4. 输出复核报告（JSON 格式）
```

### 6.2 输出报告格式

每个 Agent 输出一份报告，包含：

```json
{
  "batch": "3335",
  "offset": 0,
  "image_range": "3335_001.png ~ 3335_074.png",
  "total_green_checked": 44,
  "total_red_checked": 0,
  "results": {
    "green_confirmed": 40,      // 图片中确认存在，数据正确
    "green_corrected": 3,       // 图片中存在但数据有差异，需修正
    "green_not_found": 1,       // 图片中未找到，可能是误补
    "red_is_ocr_error": 0,      // 红色行实际是 OCR 错误（有绿色配对）
    "red_truly_excess": 0,      // 红色行确实不在图片中
    "red_actually_valid": 0     // 红色行在图片中存在，不应标红
  },
  "details": [
    {
      "page": 10,
      "image": "3335_010.png",
      "printed_page": "— 10 —",
      "items": [
        {
          "row": 75,
          "type": "green",
          "school": "2161",
          "spec": "06",
          "verdict": "confirmed",
          "note": "图片中确认存在，数据完全一致"
        }
      ]
    }
  ]
}
```

### 6.3 修正操作

本轮**只做验证，不直接修改 xlsx**。所有复核结果汇总后，统一由一个汇总脚本批量修正：
- `green_confirmed` → 保留，去掉绿色标记
- `green_corrected` → 修正字段值后保留
- `green_not_found` → 标记待人工确认（不直接删除）
- `red_is_ocr_error` → 删除红色行（已有绿色正确版本）
- `red_truly_excess` → 保留红色标记
- `red_actually_valid` → 去掉红色标记，改为正常行
